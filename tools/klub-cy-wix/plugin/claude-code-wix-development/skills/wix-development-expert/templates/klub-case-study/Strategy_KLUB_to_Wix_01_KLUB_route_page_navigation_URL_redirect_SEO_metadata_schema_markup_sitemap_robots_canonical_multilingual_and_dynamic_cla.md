# KLUB to Wix Migration Design: Routes, Navigation, URLs, and SEO

## 1. Architecture Context

This route plan assumes the leading destination from the approved blueprint: **Wix-managed Headless with the full Astro integration**. The existing Astro route and component structure should be preserved unless a route change is explicitly approved. A separate editor-native Wix Studio implementation would require a different page/menu mapping and must not be implied by this document.

## 2. Verified Route Accounting

The KLUB repository contains **14 route source files**. These produce **17 built HTML documents**: 12 ordinary static public pages, one 404 document, and four current class-detail pages generated by the dynamic class route.

## 3. Dynamic Class Pages

Create a Wix CMS `Classes` collection containing the four verified editorial class records. Preserve each source slug and stable `sourceId`. The route contract remains `/classes/{slug}/` unless an approved Wix limitation makes a change unavoidable.

The class listing and detail pages should continue to render from Astro routes. Wix CMS is the content authority; an optional Wix Bookings service is a separate operational entity linked through a crosswalk. Do not make the dynamic page dependent on Wix Bookings unless the Bsport-versus-Wix-Bookings decision is approved.

The route generator must:

1. page through all class records when the API requires pagination;
2. reject duplicate or invalid slugs before build/release;
3. produce the four expected current class-detail outputs;
4. define behavior for an unpublished or missing class;
5. preserve the source ordering or an approved `sortOrder`;
6. generate source-backed metadata and structured data without invented claims.

## 4. Navigation and Shared Chrome

Keep the shared Headless header and footer component model. Do not replace `src/components/Header.astro` with a native Wix Site Menu unless the project is explicitly converted to an editor-native implementation.

Preserve and test:

- desktop navigation order and labels;
- mobile menu open/close state, focus containment, Escape behavior, and focus return;
- active/current-page indication;
- direct class, timetable, booking, about, location, pricing, and contact links;
- footer navigation and business/contact facts;
- sticky CTA, WhatsApp, social links, and external-link behavior;
- trailing-slash policy and relative/absolute URL normalization.

A navigation change requires a route-manifest update and link-crawl evidence.

## 5. Titles, Descriptions, Canonicals, and Social Metadata

The source derives metadata through the Astro layout and page-specific data. Preserve this code-first pattern under the Wix Astro SEO integration. Map source values explicitly rather than assuming Wix will reconstruct them.

| Surface | Migration requirement |
|---|---|
| `<title>` | Preserve approved page/class values |
| Meta description | Preserve source value or approved source-backed fallback |
| Canonical | Use the final public URL after domain approval; no staging canonical on production |
| Open Graph title/description/image | Preserve approved values and verify the media is publicly accessible |
| Social/Twitter metadata | Preserve existing behavior and validate rendered output |
| Language/locale | Preserve verified source language and country/locale settings |
| Robots | Keep preview/nonproduction indexing policy separate from live |
| Sitemap | Include all 16 canonical public pages and exclude error/private URLs |

The source canonical host is currently recorded as `https://www.keeplivingunderbalance.com`. Treat this as a source fact, not authorization to connect or change the domain. Confirm domain ownership, final host choice, redirects, and DNS before release.

## 6. Structured Data

Preserve the source-backed `ExerciseGym`/local-business information and the FAQ structured data only when every value is verified and visible/appropriate for the page. Render valid JSON-LD and test the final public output.

Do not label arbitrary `<script type="application/ld+json">` insertion as a “custom meta tag.” Under Headless Astro, emit JSON-LD from the layout or page code and protect serialization. If an editor-native alternative is later selected, retrieve the current Wix SEO/structured-data instructions for that environment.

Required validation includes JSON parsing, schema type, URL/image reachability, duplicate entity review, source-to-rendered value comparison, and search-engine test-tool review where applicable.

## 7. Sitemap and Robots

Confirm the current Wix-managed Astro SEO integration and generated-file behavior before implementation. The target contract is:

- `/sitemap.xml` or the current documented sitemap endpoint lists the 16 canonical public pages;
- all four class-detail URLs are present;
- 404, preview-only, private/member-only, and duplicate URLs are excluded;
- `robots.txt` references the correct live sitemap and does not accidentally block public assets or pages;
- preview and temporary domains are not indexed contrary to the release plan.

Do not assume that moving to Wix automatically makes a repository-generated sitemap or robots file correct.

## 8. Redirect Strategy

Prefer one-to-one URL preservation. Create a redirect only for an approved route change, consolidated duplicate, trailing-slash normalization, or domain/host transition.

The redirect manifest must contain source URL, destination URL, status, reason, source evidence, owner, validation state, and rollback treatment. Avoid chains, loops, broad regex rules, and redirects to unrelated landing pages. Retrieve the current Wix redirect/site-URL method schema or configure redirects using the documented Wix-managed Headless mechanism; do not invent an API name such as `manage-url-redirects`.

## 9. Multilingual Boundary

The acquired KLUB route/content inventory does not establish a multilingual route set. Do not add language prefixes, hreflang tags, or translated CMS records without a verified content and URL strategy. If multilingual support is requested later, define locales, default language, slug policy, fallback behavior, translated fields, canonical/hreflang clusters, sitemap entries, and editor ownership before implementation.

## 10. Automation and Manual Work

| Work item | Automation potential | Human/approval dependency |
|---|---|---|
| Route extraction and build-output inventory | Deterministic repository scripts | Review dynamic and error-route interpretation |
| Link crawl and status validation | Browser/HTTP automation | Approve intentional external/booking behavior |
| Metadata and JSON-LD extraction | Deterministic parsing and browser capture | Approve business/legal claims |
| Redirect manifest generation | Deterministic diff | Approve every nontrivial route change |
| CMS class route generation | Code and read-only data validation | Approve schema and writes |
| Navigation implementation | Code reuse | Visual/accessibility sign-off |
| Domain/canonical cutover | API/UI plus DNS process | Explicit domain/DNS confirmation |

## 11. Acceptance Criteria

The route and SEO workstream passes only when:

1. all 14 route source files are accounted for;
2. the target build produces the expected 17 documents or an approved equivalent;
3. the 16 public canonical pages return the intended successful responses;
4. missing paths return the migrated 404 content with a true 404 response;
5. the four `/classes/{slug}/` pages match the four approved CMS records;
6. desktop and mobile navigation, focus behavior, and shared chrome pass;
7. every public page has approved title, description, canonical, and social metadata;
8. FAQ and business structured data validate with source-backed values;
9. sitemap and robots reflect the final live environment;
10. redirects have no loops/chains and pass source-to-target checks;
11. no staging domain, Wix temporary URL, or obsolete host is emitted as the production canonical;
12. the final domain decision and DNS/cutover plan are approved.

## 12. Evidence and Limitations

The repository inventory, mapping summary, build output, and Playwright baseline support this plan. They do not prove that a destination Wix project has been created or that production routes, SEO, redirects, or the domain have been implemented. Until live preview and public verification exist, describe this as a migration design and acceptance contract.
