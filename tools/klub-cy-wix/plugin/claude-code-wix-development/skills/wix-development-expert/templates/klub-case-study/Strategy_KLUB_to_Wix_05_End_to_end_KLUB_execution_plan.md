# KLUB to Wix: End-to-End Controlled Execution Plan

## 1. Status and Intended Destination

The validated KLUB repository is an Astro site with 14 route source files, four structured JSON content files, ten reusable components, 87 public assets, a Bsport booking embed, Netlify-form behavior, analytics hooks, structured data, and a Playwright regression suite. Its production build succeeds; the acquired source baseline completed **862 Playwright tests with 45 skips**.

The leading migration path is **Wix-managed Headless with the full Astro integration**. This preserves KLUB’s existing route/component/frontend architecture while adding Wix-managed hosting, automatic visitor/member authentication, Wix business APIs, deploy previews, and Wix CLI operations. A native Wix Studio rebuild is an alternative only if the owner explicitly prioritizes editor-canvas maintenance over code/visual parity. It is not the default selected by this plan.

No live Wix site, schema, media, CMS record, booking service, form, domain, or publication has been created by this project. The available Wix account/site, business-system choice, credentials, permissions, and approvals remain required before write phases.

## 3. Official Replatform Utilities and Their Boundaries

Selected files from Wix’s official replatform resources are bundled under:

```text
templates/official-wix-replatform/
├── wix-headless-replatform/
└── wix-replatform/
```

The full research workspace uses `sources/wix-skills/` as the provenance location. These are reference utilities with their own prerequisites and contracts; they are not all direct KLUB migration commands.

| Utility | Verified purpose | KLUB use |
|---|---|---|
| `wix-headless-replatform/scripts/extract-assets.mjs` | Fetches a source URL, discovers HTML/CSS/font assets, optionally downloads them, and writes extraction manifests | Optional source-site cross-check; it does **not** upload to Wix. KLUB repository assets remain the primary inventory |
| `wix-headless-replatform/scripts/extract-seo.mjs` | Fetches a source URL and writes extracted SEO evidence | Optional live-source verification before freeze/cutover |
| `wix-headless-replatform/scripts/visual-qa.mjs` | Scores frozen extraction/build-plan/ledger evidence and emits a heuristic preflight report | Use only after producing its required extraction contract. Its own output says browser-backed result comparison is still required |
| `wix-headless-replatform/scripts/provision-repeater-cms.mjs` | Reads a generated `repeater-cms.json`; defaults to dry-run and can create a generic repeater schema with `--execute` | **Do not execute for KLUB classes/FAQ/pricing.** The generic fields and permissions do not match the approved KLUB CMS design; retain it as a reference implementation only |
| `examples/migration/src/build-klub-payloads.mjs` | Reads the four verified KLUB JSON sources and creates deterministic candidate payloads with source IDs and hashes | Approved read-only KLUB transform; no Wix calls |

Before running any official utility, read its source and local documentation, install dependencies in an isolated checkout, pin the version/commit, and review network/file/write behavior. A referenced utility does not supersede the full current Wix API method schema.

3. Preserve content record counts and hashes.

## 5. Phase 1: Destination Discovery and Architecture Approval

Read-only discovery must resolve:

| Input | Required result |
|---|---|
| Wix account | Immutable account ID and owner/collaborator identity |
| Destination | Existing site/project or approved new Wix-managed Headless project |
| Framework support | Current Wix-managed Astro/Node/package compatibility |
| Business solutions | CMS plus any installed/desired Forms, Bookings, Members, Pricing Plans, CRM, analytics |
| Auth | Wix-managed Astro private-app flow and any elevated server operations |
| Operations | Development/preview/live environments, domain, DNS owner, rollback owner |
| Commercial choice | Keep Bsport, replace with Wix Bookings, or approved hybrid |
| Editorial choice | Wix CMS field/relation strategy and future editor ownership |

Create a written decision record. Do not create a project or install apps until the target, impact, and approval are explicit.

## 6. Phase 2: Scaffold and Prove a No-Write Build

1. Create or connect a Wix-managed Astro project only after approval.
2. Start from the current official Wix scaffold/package set; do not paste snapshot versions.
3. Port KLUB routes, layouts, components, styles, and public assets without changing content authority yet.
4. Replace hosting-specific Netlify configuration with Wix-managed equivalents only after confirming forms, redirects, headers, and runtime behavior.
5. Run type checks, unit tests, Astro/Wix build, and a smoke test against local/preview output.
6. Prove that no secret is in browser-delivered code and no write runs at import/build time.

This phase can use local fixture JSON while CMS schemas and writes remain unapproved.

## 7. Phase 3: Approve CMS Schemas and Read-Only Payloads

Use the corrected CMS strategy:

- `Classes` is the canonical editorial class-page model.
- `FaqSections` and `FaqItems` preserve section/item order.
- `PricingGroups` and `PricingItems` preserve editorial pricing.
- `SiteSettings` holds approved frontend settings.
- A Wix Bookings service, if adopted, is a separate operational entity linked by a stable crosswalk.

Run the deterministic KLUB transformer:

```bash
cd templates/examples/migration
node src/build-klub-payloads.mjs --help
npm run build-payloads -- /path/to/KLUB ./output
```

Expected dry-run counts are 4 classes, 6 FAQ sections, 38 FAQ items, 4 pricing groups, 12 pricing items, and one settings record. Review payloads, logical collection schemas, permissions, relations, and the source-to-Wix crosswalk before any Wix method is called.

## 8. Phase 4: Approval-Gated Wix Writes

Perform writes in dependency order:

1. Create/verify the approved CMS collections and indexes.
2. Upload approved media and record the source-to-Wix media crosswalk.
3. Upsert CMS records by stable `sourceId`; never use create-only retries that duplicate data.
4. Resolve parent/child relations and media references.
5. Read back every collection, count, relation, slug, and failure.
6. Configure Forms/CRM only after field, consent, notification, and retention approval.
7. Configure Wix Bookings/Pricing Plans only if the operational migration is explicitly selected and separately mapped.

Each batch requires the current method schema, target site ID, exact count, sanitized payload, idempotency key, validation query, and rollback limitation. Preserve an operation log and stop on systemic errors.

## 9. Phase 5: Frontend Integration

Replace fixture JSON with direct Wix SDK module calls under Wix-managed Astro authentication. Keep privileged calls server-side and elevate only documented methods after permission review. Trim SDK responses before serializing them to client islands.

Preserve:

- the 16 public canonical URL outputs and 404 behavior;
- navigation, footer, sticky CTA, WhatsApp, forms, and booking destinations;
- typography, spacing, colors, imagery, responsive layout, and motion rules;
- titles, descriptions, canonicals, social metadata, structured data, sitemap, robots, and redirects;
- keyboard behavior, landmarks, labels, focus states, reduced motion, alt text, and contrast.

Do not claim an editor-native Studio page or component exists unless it was actually built and inspected.

## 10. Phase 6: Validation and Test-Parity Strategy

The **862 passing / 45 skipped** result is the source baseline. Do not promise that all 862 selectors run unchanged against a Wix-hosted build. Many tests may target source DOM details or the original Netlify environment.

Use three layers:

| Layer | Requirement |
|---|---|
| Source regression | Keep the original KLUB suite passing against the frozen source while migration work proceeds |
| Target contract suite | Build route, content, metadata, accessibility, form, booking, link, asset, and interaction tests against the Wix preview |
| Selector portability review | Classify each existing Playwright test as reusable unchanged, reusable with base URL/config, adaptable, source-only, or obsolete with written justification |

At minimum, verify 16 canonical public pages, four class records/pages, the not-found state/status, responsive viewports, keyboard paths, form submissions to the intended system, booking journey, analytics/consent behavior, SEO metadata, structured data, redirects, and all internal links. Use screenshot comparisons and manual review; the official `visual-qa.mjs` is only a frozen-spec preflight.

## 11. Phase 7: Preview, Release, Domain, and Rollback

A stable Wix preview must pass the target contract suite and human visual/business review. Release, domain connection, DNS changes, and publication are separate sensitive operations.

The cutover packet must contain:

- target account/site/project IDs;
- approved release/build identifier;
- final route and redirect manifests;
- CMS/media/business-system reconciliation;
- domain/DNS records, current TTLs, and owner;
- monitoring/log/analytics plan;
- rollback decision and time window;
- retained prior Astro/Netlify deployment and instructions for reverting traffic.

After cutover, verify the public domain, TLS, canonical URLs, robots/sitemap, forms, Bsport or Wix Bookings, analytics/consent, performance, and error monitoring. DNS reversal is not an instantaneous or complete rollback; document propagation, changed data, submissions, and transactions that cannot be reversed by DNS alone.

## 12. Blockers and Unresolved Decisions

| Decision | Why it blocks writes or release |
|---|---|
| Destination Wix account/site/project | Prevents target resolution and permission checks |
| Bsport versus Wix Bookings | Determines schedule, capacity, pricing, member, payment, and operational migration |
| Forms/CRM design | Determines fields, consent, spam, notifications, automations, and retention |
| CMS schema details | Determines collection creation and payload transformation |
| Domain/DNS ownership | Determines cutover and rollback control |
| Analytics and consent | Determines legal/technical implementation and parity |
| Content owner and maintenance workflow | Determines whether Headless CMS editing meets the long-term requirement |
| Payment/tax/refund policy | Prevents a safe Bookings/Pricing Plans commerce migration |

These inputs do not block read-only source analysis, payload generation, architecture comparison, or local frontend preparation. They do block the affected live Wix operations and production completion claim.

## 13. Completion Definition

KLUB is migrated only when:

1. the selected Wix architecture and business-system choices are approved;
2. CMS/media/business records reconcile with deterministic source manifests;
3. all 16 public canonical page outputs and the 404 behavior are verified;
4. visual, responsive, accessibility, SEO, form, booking, analytics, and consent contracts pass;
5. preview and production states are inspected;
6. domain/redirect cutover evidence is saved;
7. rollback and irreversible-data limitations are documented;
8. no high-severity unresolved gap remains.

Until those conditions are met, describe the deliverable as a **validated migration corpus, implementation blueprint, read-only payload set, and installable skills**, not a completed Wix migration.
